======================================================================
0. PURPOSE OF THIS DOCUMENT
======================================================================

This document is the master implementation blueprint for converting the
supplied paper-based Faculty Self-Appraisal & Assessment Report into a
polished, production-quality institutional web application.

The objective is NOT to make a simple HTML copy of the PDF.

The objective is to build a complete Faculty Self-Appraisal & Assessment
Management System that preserves the official fields, terminology,
appraisal categories, cadre-wise maximum marks, declaration/review
structure and supporting-document requirements from the supplied form,
while turning the manual process into a secure, maintainable,
easy-to-use digital workflow.

The product must feel like professional institutional software: -
exceptionally clean visual design - excellent information hierarchy -
low cognitive load - fast and responsive interaction - predictable
navigation - excellent form UX - accessible and responsive - easy for
faculty to understand without training - easy for HoD/Principal to
review - easy for developers to maintain - configurable rather than
hard-coded wherever policy may change - auditable and secure - suitable
for future expansion to other departments

IMPORTANT SOURCE BOUNDARY: The supplied six-page document defines the
official form structure and cadre-wise maximum marks. It does NOT, by
itself, define every formula used to convert activities into
self-scores. Do not invent institutional scoring rules. Treat missing
rules as configuration/requirements questions that must be confirmed by
the institution.

====================================================================== 1.
PRODUCT VISION
======================================================================

Working product name: Faculty Appraisal Management System (FAMS)

Alternative formal name: Faculty Self-Appraisal & Assessment Management
System

Core promise: Replace a difficult paper-based appraisal process with a
guided, auditable, role-based digital workflow without changing the
institution’s official appraisal structure.

The system should make these actions easy:

FACULTY: 1. Start an appraisal for an academic year. 2. Complete
information section by section. 3. Add unlimited records to repeated
tables. 4. Save automatically. 5. Upload evidence. 6. See completion
status. 7. Review all information before submission. 8. Submit once
complete. 9. Receive returned items and correction instructions. 10.
Track appraisal status. 11. Download/preview the final report where
permitted.

HOD: 1. See submissions requiring review. 2. Open a complete appraisal.
3. Review every section. 4. Inspect supporting evidence. 5. Add remarks.
6. Return the appraisal for correction. 7. Recommend/approve according
to institutional workflow. 8. Track pending and completed appraisals.

PRINCIPAL: 1. See appraisals reaching principal review. 2. Review the
complete record. 3. Inspect evidence. 4. Add remarks. 5. Approve or
return according to institutional rules.

ADMINISTRATOR: Only if the institution authorizes this role: 1. Manage
users. 2. Manage departments. 3. Manage academic years. 4. Manage cadre
configuration. 5. Manage appraisal configuration. 6. Manage
policy/configuration without modifying historical records. 7. Monitor
system activity.

DO NOT INVENT ANSWERS.

Ask the Vice HOD / authorized stakeholder:

A. Identity and authentication 1. Should the system use college email
accounts? 2. Is there an existing college login/SSO? 3. Who creates
faculty accounts? 4. Are HoD and Principal accounts centrally managed?
5. Can one person have more than one role?

B. Appraisal lifecycle 6. Is one appraisal allowed per faculty per
academic year? 7. Can a faculty create a new appraisal after final
approval? 8. Does submission lock editing? 9. Can HoD return an
appraisal? 10. Can Principal return an appraisal? 11. Can faculty edit
only returned sections or the entire appraisal? 12. Is HoD approval
mandatory before Principal review? 13. What happens after Principal
return? 14. Is final approval irreversible?

C. Scoring 15. What is the exact self-score calculation method for every
criterion? 16. Are there sub-criteria? 17. Are there minimum/maximum
values for individual activities? 18. Does the system calculate scores
automatically or merely validate them? 19. Can HoD modify a faculty’s
self-score? 20. Is a separate panel score required later? 21. Does the
scoring policy vary by academic year?

D. Evidence 22. Which documents are mandatory? 23. Allowed file types?
24. Maximum file size? 25. Can multiple documents be attached to one
record? 26. Should evidence be visible to HoD and Principal? 27. Can
evidence be replaced after submission? 28. Should final documents be
retained indefinitely?

E. Reporting 29. Must the final PDF visually match the official six-page
form? 30. Should the system generate a PDF before final approval, after
approval, or both? 31. Should the PDF include digital signatures? 32.
Should HoD/Principal remarks appear in the PDF? 33. Should the system
generate department-level reports?

F. Institutional scope 34. Is version 1 only for CSE? 35. Should
departments be configurable? 36. Will the same system eventually serve
the entire college? 37. Are department-specific fields allowed?

======================================================================

system:

equivalent controlled component system - React Hook Form - Zod -
TanStack Query where appropriate

BACKEND Preferred enterprise-oriented option: - Spring Boot - Java 25 -
Spring Security - Spring Data JPA / Hibernate - Bean Validation - REST
API

DATABASE - MySQL 8

DOCUMENT STORAGE Development: - local/private filesystem abstraction

Production: - object storage or institution-approved file storage

PDF: - server-side PDF generation from structured appraisal data

DEPLOYMENT: - Docker where appropriate - reverse proxy - HTTPS -
environment-based configuration - database backup strategy

IMPORTANT: Do not introduce microservices just to look advanced. A
modular monolith is appropriate for this application and is easier to
develop, test, deploy and maintain.

CANNOT: - access another faculty’s appraisal - change own role - change
scoring policy - approve own appraisal - alter audit history - modify
approved records unless institutional workflow explicitly permits it

HOD

CAN: - view assigned faculty - view submitted appraisals - review
evidence - add review remarks - return appraisal - approve/recommend
according to workflow - view history - filter/search appraisals

CANNOT: - silently alter faculty-entered information - impersonate
faculty - modify policy unless separately authorized - delete audit
history

PRINCIPAL

CAN: - view appraisals reaching principal stage - review complete
appraisal - view evidence - add remarks - approve/return according to
workflow

ADMIN

Only if approved: - manage users - manage departments - manage academic
years - configure policies - manage system configuration - view audit
logs - manage system-level settings

Never make ADMIN a shortcut around business rules.

8. APPRAISAL STATE MACHINE
======================================================================

Recommended states:

DRAFT SUBMITTED HOD_REVIEW HOD_RETURNED HOD_APPROVED PRINCIPAL_REVIEW
PRINCIPAL_RETURNED APPROVED

Optional: WITHDRAWN ARCHIVED

State transition rules must be enforced on the backend.

Example:

DRAFT -> SUBMITTED

SUBMITTED -> HOD_REVIEW

HOD_REVIEW -> HOD_RETURNED -> HOD_APPROVED

HOD_RETURNED -> DRAFT / RESUBMITTED according to chosen implementation

HOD_APPROVED -> PRINCIPAL_REVIEW

PRINCIPAL_REVIEW -> PRINCIPAL_RETURNED -> APPROVED

PRINCIPAL_RETURNED -> RESUBMITTED / HOD_REVIEW according to approved
workflow

Every transition: - actor - timestamp - old state - new state -
reason/comment must be stored.

12. FORM UX RULES
======================================================================

1.  Group related information.
2.  Use labels, not placeholder-only fields.
3.  Explain unusual fields with small helper text.
4.  Avoid asking for the same information twice.
5.  Prefill profile information.
6.  Make repeated data dynamic.
7.  Use conditional fields.
8.  Validate at field level where possible.
9.  Validate section before allowing progression.
10. Validate the entire appraisal on submission.
11. Preserve entered data if validation fails.
12. Never silently discard user input.
13. Avoid excessive modal dialogs.
14. Use confirmation only for destructive/high-impact actions.
15. Provide keyboard-accessible controls.
16. Maintain focus intelligently after errors.
17. Make date formats consistent.
18. Make percentages explicit.
19. Clearly distinguish optional and required fields.
20. Never use unexplained abbreviations in the UI.

======================================================================

Number of sections: - non-negative integer

Number of students: - non-negative integer

Amount: - non-negative decimal - correct currency handling

Date range: - end >= start

Year: - valid academic/year format

Score: - score >= 0 - score <= configured maximum

Text: - reasonable length - reject dangerous content where applicable

Files: - allowlist extensions - verify MIME type server-side - size

======================================================================
16. AUTOSAVE
======================================================================

Autosave must be implemented carefully.

Recommended behavior: - debounce saves after meaningful changes - save
section-level data - show save state - recover draft after refresh -
handle network failure - avoid creating excessive revisions

Suggested UI: “Saved” “Saving…” “Offline — changes will retry” “Save
failed — Retry”

Do not make autosave compete with the user’s typing.

Never show a false “Saved” state before the backend confirms
persistence.

18. DATABASE DESIGN PRINCIPLES
======================================================================

1.  Use foreign keys.
2.  Add unique constraints where appropriate.
3.  Prevent duplicate appraisal for faculty + academic year if that is
    the institutional rule.
4.  Index frequently filtered fields.
5.  Use transactions for important state transitions.
6.  Avoid storing repeated records as JSON blobs unless the data is
    genuinely configuration or flexible metadata.
7.  Store dates in a consistent database representation.
8.  Do not store uploaded files directly in database BLOBs unless there
    is a deliberate institutional reason.
9.  Store file metadata and secure storage keys.
10. Preserve historical scoring-policy references.
11. Use soft deletion carefully for records that may be required for
    audit.
12. Never physically delete audit history.
